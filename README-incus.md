# Использование Incus с файловой системой Btrfs на Raspberry Pi 5

Этот документ объясняет архитектуру хранения данных в нашем проекте автоматизации и описывает преимущества использования файловой системы **Btrfs** на накопителях **NVMe** для управления контейнерами LXC и виртуальными машинами QEMU через **Incus**.

---

## Архитектура хранилища

При развертывании кластера или одиночного сервера наш скрипт автоматизации `rpi5imager.sh` выполняет следующие действия:
1. Инициализирует систему на MicroSD-карте (ext4).
2. Форматирует скоростной накопитель **NVMe в файловую систему Btrfs**.
3. Переносит рабочую систему на NVMe, создавая производительную базу для контейнеров и виртуальных машин.

Когда вы инициализируете Incus (`incus admin init`), утилита автоматически определяет, что базовая система работает на Btrfs, и настраивает пул хранения (`storage pool`) типа `btrfs`. Это открывает доступ к продвинутым технологиям управления данными на уровне ядра Linux.

---

## Ключевые преимущества Btrfs для LXC и QEMU в среде Incus

### 1. Мгновенное клонирование и создание инстансов (Copy-on-Write)
Btrfs использует механизм **Copy-on-Write (CoW)**. 
* **Как это работает:** Когда вы запускаете новый контейнер из образа или клонируете существующую виртуальную машину, Incus не копирует физические файлы на диске. Вместо этого создается субтом-клон (subvolume clone), который просто ссылается на уже существующие блоки данных.
* **Результат:** Развертывание нового контейнера LXC или виртуалки QEMU занимает **менее 1 секунды**, независимо от размера исходного образа. Дисковое пространство начинает расходоваться только тогда, когда внутри нового инстанса изменяются или добавляются файлы.

### 2. Атомарные и легковесные снимки системы (Snapshots)
Перед обновлением приложений или экспериментами с конфигурацией вы можете делать снимки состояния инстансов (`incus snapshot create`).
* На Btrfs создание снимка происходит **мгновенно** и не вызывает задержек в работе контейнера (I/O freeze), так как это просто фиксация метаданных ядра.
* Снимки не занимают места на NVMe-диске в момент создания. Они увеличивают объем занятого пространства только по мере того, как контейнер генерирует новые данные, перезаписывая старые блоки.

### 3. Прозрачное сжатие данных (Transparent Compression)
По умолчанию в Btrfs можно включить сжатие на лету (например, `zstd`).
* **Экономия места:** Файлы операционных систем внутри контейнеров (логи, бинарники, библиотеки) сжимаются очень эффективно. Это позволяет уместить на один NVMe-накопитель в 1.5–2.6 раза больше изолированных систем.
* **Увеличение скорости чтения:** Процессор Broadcom BCM2712 на Raspberry Pi 5 имеет 4 производительных ядра. Ему гораздо быстрее считать сжатый блок данных из NVMe и распаковать его в оперативной памяти, чем читать несжатый массивный файл с диска. Это снижает нагрузку на шину PCIe.

### 4. Оптимизация работы виртуальных машин QEMU
Виртуальные машины (в отличие от контейнеров) используют тяжелые файлы виртуальных дисков (образы `.img`/`.qcow2`). 
* В обычных файловых системах (вроде ext4) клонирование виртуальной машины на 20-50 ГБ приводит к долгому физическому копированию гигабайт данных, что изнашивает NVMe.
* В Btrfs Incus использует команду `reflink`, копируя только указатели на блоки. Для QEMU-машин это означает моментальный бэкап и дублирование окружений без деградации производительности диска.

### 5. Эффективная репликация в кластере (Btrfs Send/Receive)
Если вы объединяете несколько Raspberry Pi 5 в один кластер Incus, Btrfs делает миграцию контейнеров между серверами невероятно быстрой.
* При переносе контейнера с одной ноды на другую Incus использует встроенные команды `btrfs send` и `btrfs receive`. Вместо анализа миллионов мелких файлов отправляется чистый поток измененных блоков данных на уровне файловой системы.

## Использование MicroSD (ext4) как «золотого образа» для репликации нод

Архитектура нашего проекта позволяет использовать стандартную MicroSD-карту (`mmcblk0`), отформатированную в `ext4` и содержащую предустановленных пользователей, ключи SSH, сетевые утилиты, компиляторы (`mise`, `rust`, `build-essential`), в качестве **шаблона (Golden Image)** для быстрого масштабирования кластера.

### Преимущества такого подхода:
* **Идентичность нод (Homogeneous Cluster):** Все новые Raspberry Pi 5 загружаются с абсолютно одинаковым набором предустановленного софта, системных пользователей и настроек безопасности.
* **Быстрая замена оборудования (Disaster Recovery):** Если одна из Raspberry Pi 5 или её NVMe-накопитель выйдут из строя, вам достаточно вставить копию «золотой» MicroSD-карты в новую плату, подключить новый NVMe, запустить `rpi5imager.sh` и заново привязать ноду к кластеру. Это занимает не более 5 минут.
* **Разделение рисков:** Ошибки или сбои файловой системы Btrfs внутри контейнеров (например, при критическом переполнении диска) никак не затронут загрузочную MicroSD-карту. Хост-система всегда останется доступна для управления по SSH.

## Пайплайн развертывания новой ноды из образа

Когда вы разворачиваете новую плату Raspberry Pi 5 из подготовленного «золотого образа» MicroSD, процесс инициализации и вступления в кластер выглядит следующим образом:

1. **Запись образа:** Запишите ваш кастомный `ext4`-образ на MicroSD-карту новой ноды.
2. **Настройка сетевого моста:** Запустите скрипт настройки сети:
   ```bash
   sudo ./nmcli-br0.sh
   ```
   *(Мост `br0` поднимется автоматически с заданными параметрами без задержки STP).*
3. **Подготовка NVMe-накопителя:** Запустите ваш скрипт разметки и миграции:
   ```bash
   sudo ./rpi5imager.sh
   ```
   *(База хранилища для Btrfs готова).*
4. **Смена Hostname и вступление в кластер:** Сгенерируйте токен на лидере кластера (`incus cluster add <имя>`) и запустите итоговый скрипт с флагом `--name`. Скрипт сам изменит имя хоста системы через `hostnamectl` и зарегистрирует узел в кластере под новым именем:
   ```bash
   sudo ./incus-init.sh --name rpi5-node3
   ```
   *Если вы хотите сохранить текущее имя хоста, просто запустите скрипт без параметров:* `sudo ./incus-init.sh`.

## Сводное сравнение: Btrfs против стандартного Dir (ext4)

| Возможность | Использование директории (стандартный ext4) | Пул хранения Btrfs (наш проект) |
| :--- | :--- | :--- |
| **Скорость создания контейнера** | Медленная (требуется физическое извлечение и копирование всех файлов) | **Мгновенная** (менее секунды через CoW-субтома) |
| **Создание снимков (Snapshots)** | Медленное дублирование файлов | **Мгновенное** (фиксация метаданных) |
| **Эффективность хранения снимков** | Занимает полный объем файлов (100% дублирование) | Занимает место **только под измененные данные** (дельта) |
| **Сжатие данных на диске** | Нет | **Да (zstd)** — экономит место и ресурс NVMe |
| **Клонирование дисков QEMU** | Долгое чтение и запись всего файла диска | **Мгновенно** через механизм `reflink` |

## Как проверить статус хранилища после инициализации

После успешного выполнения скриптов автоматизации сети и инициализации Incus, вы можете убедиться, что пул настроен правильно, выполнив команду:

```bash
incus storage list
```

Вы должны увидеть пусковую область `default` с типом драйвера `btrfs`:
```text
+---------+--------+-----------------------+-------------+---------+---------+

|  NAME   | DRIVER |        SOURCE         | DESCRIPTION | USED BY | STATE   |
+---------+--------+-----------------------+-------------+---------+---------+

| default | btrfs  | /var/lib/incus/sto... |             | 1       | CREATED |
+---------+--------+-----------------------+-------------+---------+---------+
```

Для просмотра детальной информации о свободном месте и сжатии на самом NVMe-накопителе используйте системную команду:
```bash
sudo btrfs filesystem usage /
```
